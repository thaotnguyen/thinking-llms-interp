  FINDING 1 (the key one): NO LLM FORWARD PASS IS NEEDED.
    Each activations pkl is a 4-tuple:
      [0] ndarray (N,d) float32 — per-sentence mean-pooled activations
      [1] list[str] — the N sentence texts
      [2] list[(pmcid, sentence_idx)] — row provenance
      [3] ndarray (1,d) float32 — the centering mean vector
    Every row has L2 norm EXACTLY 1.000000, i.e. already mean-centered and
    L2-normalised — which is precisely the space the SAE consumes.
    So annotate_thinking.py's full nnsight trace through the model is redundant.
    Encoding reduces to one (N,d)@(d,K) GEMM per SAE: ~0.8 TFLOP per model, under a
    second of math. The job is 100% disk-bound. This is why the 4x RTX 5090s sat idle
    during phase 1 — a GPU cannot make a disk-bound job faster.

  FINDING 2: annotate_thinking.py is currently BROKEN.
    Line 98 calls split_into_sentences(thinking_process, min_words=1), but the function
    (utils/utils.py:1076) takes ONE argument — min_words was dropped when the splitter
    moved to PyRuSH. The TypeError is swallowed by a broad `except Exception`, so the
    script prints an error per response and writes an empty []. Same latent bug at

  FINDING 3: n_clusters IS the SAE latent count (num_latents == K <= 20), so "all
    latents" is a <=20-dim vector. And the SAE has NO ReLU (encode = encoder(x-b_dec)
    .topk(k)), so latent values are SIGNED pre-activations.

STEP 5 — Wrote annotate-saes/encode_latents.py
  Design:
    - numpy-only. /usr/bin/python3 has numpy 2.4.6. Reads torch .pt checkpoints WITHOUT
      torch via zipfile + a custom Unpickler that maps storage types to numpy dtypes.
      Staying off CUDA also removes the entire TF32 precision-risk surface on Blackwell.
    - Reads each layer's pkl ONCE and applies all 6 K's to it: 54 reads, not 324.
    - PRECISION: accumulates in float64, stores float32. Does NOT fold b_dec into the
      bias — W(x-b)+c and Wx+(c-Wb) are algebraically equal but NOT float-equal, and the
      difference can flip a near-tie argmax. Reproduces the reference op order from
      utils/clustering_methods.py:592 exactly. Floats serialised with %.9g, which
      round-trips float32 exactly, so the text files lose nothing.
    - Does NOT re-center or re-normalise (rows already unit-norm); asserts it instead.

  CORRECTNESS GATES (run per model/layer/K before anything is written):
    G1 shape        — input_dim == d, num_latents == K
    G2 provenance   — ckpt mean_vector BITWISE == pkl mean vector
    G3 row count    — len(cluster_labels) == N (hard skip on mismatch; never truncate)
    G4 agreement    — recomputed argmax(encoder(x-b_dec)) vs the ckpt's own training-time
                      cluster_labels; require >= 0.999

STEP 6 — Canary run (glm layer 8), and a gate that fired
  K=12 initially FAILED my tie-margin check. I investigated rather than just loosening it:
    - the 7 disagreeing rows (of 136,945) all sit in the BOTTOM 0.03% of the top1-top2
      margin distribution (median top-1 activation is 0.620; the margins are ~1e-4);
    - fp32 and fp64 recompute agree with each other on EVERY SINGLE ROW.
    => The disagreement is in the REFERENCE labels (produced by an fp32/TF32 GPU matmul

PROBLEM A — gemma layer 18 is missing 1,340 rows
  139,460 rows vs 140,800 for gemma's other 5 layers. Root cause (investigated):
  SIX ENTIRE CoTs were dropped (390+371+310+123+96+50 = exactly 1,340). No partial CoTs.
  In shuffle order they form two consecutive runs, each headed by a very long response —
  a TRANSIENT OOM CASCADE, not a size cap (the 15 LONGEST responses all survived).
  A co-resident vLLM server serving gpt-oss-120b was pinning 130.6 of the GPU's 139.8 GiB.
  The catch-all handler at utils/utils.py:597-599 does `continue` with NO GPU cleanup
  (unlike the two OOM handlers above it at 558-596), leaking the saved layer output into
  the next iteration — which is why one failure took out 2-4 consecutive responses.

  TRAP: random.shuffle at utils/utils.py:406 is UNSEEDED. The original permutation is
  therefore unrecoverable by re-seeding. The fix must instead PIN the response order to
  the one recovered from gemma layer 10's index — otherwise the regenerated layer lands
  in a different row order and silently corrupts any positional join.

PROBLEM B — gpt-oss-20b is missing 57 of 2,073 cases
  Consistent end to end: responses (2,073) -> activations (2,016 cases / 127,497 sentences)
  -> SAE cluster_labels (127,497, exact match) -> my output. Lost once, at extraction.
  The 57 dropped cases are PRECISELY the 57 longest responses (71k-166k chars, vs a max of
  71,869 among all 2,016 survivors) — degenerate repetition loops that blew memory.
  Deterministic, not transient: all 6 gpt-oss layers dropped the identical 57, which is why
  its layers remain positionally identical to each other.
  DECISION (user): leave gpt-oss at 2,016 cases. The OOM was accidentally protective.

    idx5   62,802 rows  100.0% dup   'Hmm.' x62,795

  My phase-1 deliverable is unaffected and correct — it faithfully encodes what those SAEs
  compute. But the SAEs themselves are contaminated.

  *** HONEST CAVEAT — READ BEFORE THE ALIGNMENT STEP ***
  The residual "loop latents" (llama 1, qwq 1, glm 1, and ALL 3 of qwen3.6's) are CROSS-CASE
  duplicates, not within-CoT loops: the same short sentence appearing ONCE in each of many
  DIFFERENT CoTs (e.g. '**', "Okay, let's tackle this case."). Within-CoT dedup — the filter you
  chose — keeps those by design, and the loop-latent metric flags them anyway. So they are not
  dedup failures. qwen3.6 is the model least helped by this pass (only 4% of its rows were
  within-CoT duplicates; its problem is 15.2% one/two-word fragments). If you want those gone
  too, that needs the global-dedup and/or min_words options that were considered and declined.

  A REAL BUG FOUND IN THE ORIGINAL TRAINING CODE (utils/clustering_methods.py):
    The loss is a variance-normalised MSE:
        loss = (pred - x).pow(2).sum() / ((x - x.mean(0))**2).sum()
    Variance is UNDEFINED for a single sample: if the final minibatch has exactly ONE row then
    x - x.mean(0) == 0, the denominator is 0, and the loss is NaN. This triggers whenever
    n_train % batch_size == 1. It killed all 6 deepseek-r1-distill-llama-8b layers (n=58,369;
    58369 % 512 == 1). The same flaw is present in the ORIGINAL clustering_sae_topk — it simply
    never hit a corpus of that size. retrain_dedup.py skips any minibatch with < 2 rows (dropping
    one row of ~58,000 is numerically irrelevant) and normalises by the rows actually used.
    Also hardened main() so one failing layer no longer aborts the other 53.

  Reproduced faithfully from the reference:
    - example ranking = rows whose argmax == latent, sorted by that latent's raw
      encoder value encoder(x - b_dec)[latent], descending
      (utils/clustering.py:1118, sae_topk branch)
    - example sampling = top (200//2) + 100 sampled at random from the remainder,
      then shuffled (generate_titles_trained_clustering.py:120)

    1. ZERO subject-model forward passes. The reference `direct` path calls
       utils.load_model() + process_saved_responses() only to recompute the
       activations it needs for ranking. Every latent value is already in the
       phase-3 sidecar, so ranking is a numpy argsort. Saves loading 9 LLMs.
    2. FIXED response parser. The reference regex
           re.search(r"Title:\s*(.*?)(?:\n|$)", response)
       matches the inner "Title:" of a markdown "**Title:**", so the trailing
       "**" lands in the capture and a newline after the header yields an empty
       field. Verified against all 6 real failure modes; the new parser also
       accepts multi-line descriptions and strips the prompt's own [brackets].
    3. Sampling is SEEDED (sha1-derived, stable across processes -- note Python's

       conditions every taxonomy of a model on identical context. Each trace is
       capped at --max-trace-chars (default 8000) so the degenerate 166k-char

    5. Examples for a _dedup SAE are drawn ONLY from rows that SAE was trained on
       (index.npz['in_training']), so within-CoT repetition loops cannot dominate
       a latent's example list.
    6. raw_responses are stored next to the parsed output, so the parser can be
       revised later without re-running a single LLM call.

================================================================================
PHASE 4a: WHY vLLM CANNOT SERVE gpt-oss-120b ON THIS BOX (4x RTX 5090, sm120)
================================================================================
CONCLUSION: it cannot, and it is not a config problem. Recorded so nobody retries it.

The three ways to run the model are each independently blocked:
    MXFP4 (native)   65 GB  -> FITS, but no working sm120 MoE kernel exists
    bf16            234 GB  -> kernels fine, but DOES NOT FIT (130 GB total VRAM)
    fp8             117 GB  -> leaves 13 GB for KV+activations: infeasible

Every MXFP4 MoE backend was tried, on BOTH vllm 0.24.0 and 0.25.1:
  marlin           gptq_marlin_repack fails on sm120. Reproduced STANDALONE, outside
                   vLLM, on a plain tensor -> it is the kernel, not the model.
  triton           emits `.tile::scatter4`; ptxas: "Feature '.tile::scatter4' not
  triton_unfused   supported on .target 'sm_120a'". That op is SM100-only.
                   I traced it to triton_kernels/target_info.py: has_tma_gather() is
                   `cuda_capability_geq(10, 0)`, which is ALSO true on SM120 (major=12),
                   so SM120 wrongly takes the SM100 TMA path. Patching that (plus
                   has_native_mxfp, plus the can_use_tma carve-out in matmul_ogs.py, so
                   SM120 follows the SM90/Hopper path end-to-end) got past the PTX error
                   -- and then hit `assert num_stages >= 1`: the kernels assume SM90/SM100
                   shared memory (~228 KB/SM). The 5090 has ~100 KB. Hard resource wall;
                   going further means hand-tuning kernel tile sizes.
  humming          cuModuleLoad -> CUDA_ERROR_ILLEGAL_ADDRESS
  flashinfer_cutlass  rejects MXFP4: "kernel does not support quantization scheme
                   QuantKey(u8,scale(u8,static,GroupShape(row=1,col=32)),symmetric)xNone"
  flashinfer_trtllm / deep_gemm   sm100 / FP8-block only
  emulation        illegal memory access inside the MoE kernel. Confirmed with STOCK
                   (unpatched) triton_kernels, in both cudagraph and --enforce-eager,
                   and under two different attention backends -> not caused by my patches.
                   (It does at least prove memory is not the issue: emulation keeps MXFP4
                   storage and dequantizes on the fly -- 16.25 GiB/GPU.)

Two unrelated sm120 potholes found and fixed along the way (both real, both needed):
  - FlashInfer's *sampler* (flashinfer/sampling.py top_k_top_p_sampling_from_logits)
    dies with "FlashInfer requires GPUs with sm75 or higher" on cc 12.0 -- its
    jit/core.py check_cuda_arch rejects SM120. Fix: VLLM_USE_FLASHINFER_SAMPLER=0.
  - Same for the FlashInfer attention backend. Fix: VLLM_ATTENTION_BACKEND=TRITON_ATTN.
  - vllm 0.25.1 needs torchcodec>=0.14, which is not published for cu128. Since it wants
    the SAME torch (2.11.0) we already have, `--no-deps` + topping up flashinfer works.
    (Do NOT let it pull a cu13 torch: this driver is 570.211.01 = CUDA 12.8 max.)

State of the vLLM venv (.venv-vllm): vllm 0.25.1, torch 2.11.0+cu128, working, sees all
4 GPUs, loads the weights in ~14 s at 16 GiB/GPU. Only the MoE kernels are unusable.
The local patches to triton_kernels were REVERTED (stock reinstalled); the widened device
gate in vllm/.../gpt_oss_triton_kernels_moe.py is inert now that we do not use vLLM.

    within-trace BITWISE-identical:    0.00%
  => Exact (string,activation)-pair dedup would remove ~NOTHING (0% bitwise equal),
     undoing the dedup. String-dedup is justified precisely because within-loop
     activations are near-identical (string is a cheap exact proxy for the loop state).
     The genuinely better variant is activation NEAR-dup dedup (cosine >= ~0.99,
     string-agnostic): same loop mass, also catches cross-string loops that string
     matching misses (likely why qwen3.6 barely improved), keeps the ~7% within-trace
     repeats that are actually distinct. Offered as a future dedup mode; not yet run.

PRECISION CLARIFICATION (user Q): centering/normalization is applied ONLY to the SAE
  INPUT (the d-dim activations: (raw - mean_new)/||.||), at both train and annotate
  time (must match the SAE's domain). The saved latent values are the SAE OUTPUT
  encoder(x_normalized - b_dec): raw, signed, no ReLU, no TopK, and NOT normalized or
  centered. Same convention as the matthewshu/HF annotations. encode_all() line 175.

================================================================================
PHASE 5: NEAR-DUPLICATE DEDUPLICATION (user-requested, threshold 0.99)
================================================================================
DEFINITION OF "NEAR"
  space:     centered + L2-normalized activation space (the SAE's input space);
             cosine = dot product there. Centered with the ALL-ROWS mean for the
             mask step (well-defined before the kept set is known).
  criterion: per trace (pmcid), in sentence order, KEEP a row iff its cosine to
             every already-kept row in that trace is < 0.99; else drop (near-dup).
             String-agnostic.
  0.99:      from the qwq measurement -- within-loop repeats median cos 1.000
             (93% >= 0.99), across-trace same-string 0.85 -> 0.99 isolates loops.

EMPIRICAL FINDING (before running): near-dup vs string-dedup, layer 9
    qwq-32b   string keeps 110,442 (42.3%) | near-dup keeps 116,219 (44.5%)
              string-keeps-neardup-drops (cross-string loops string missed): 18 rows
              neardup-keeps-string-drops (same-string, activation-distinct):  5,795 rows
    qwen3.6   string keeps 156,642 (95.7%) | near-dup keeps 161,783 (98.8%)
              cross-string loops caught: 43 rows;  same-string-distinct kept: 5,184
  => Near-dup is MORE CONSERVATIVE (keeps more): it removes only near-identical loop
     states and preserves same-string repeats that string-dedup over-removes. The
     cross-string gain is tiny. It does NOT fix qwen3.6 (cross-CASE contamination,
     which no within-trace method touches). More principled, not a different taxonomy.
